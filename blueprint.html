ShopTogether · design, architecture & build plan

Shared lists that update live, on AWS for about $0 a month

You sign up with email and password, then create lists and items. You share a list by email, and everyone who has it open sees each change within a second. The backend is serverless and pay-per-use. We build it in five steps, and every step ends with something you can test on AWS.

Architecture

Two Lambdas, one table, no servers left running

The design keeps the number of parts small. That means less to deploy and less to debug, and nothing costs money while nobody uses the app.

Auth

Cognito user pool (Lite)

Email and password with email verification. The app client has no secret, so the browser calls Cognito directly with fetch. No Amplify.

First 10,000 monthly active users are free.
REST

API Gateway HTTP API

Its built-in JWT authorizer checks Cognito tokens, so we don't write or pay for an authorizer Lambda.

About a third of the price of a REST API.
Compute

2 Lambda functions

api handles every REST route with a small router. ws handles the socket events. Both use only boto3, so there is nothing to package.

arm64 and 256 MB. Fewer functions also means fewer cold starts.
Data

DynamoDB, single table

Lists, items, members, invites and socket connections share one table. Expired invites and connections are deleted for free by the table's TTL.

On-demand billing. 25 GB of storage is always free.
Live

API Gateway WebSocket

After each write, the api Lambda pushes the change straight to the people who have that list open. No streams and no extra Lambda.

Costs cents at hobby scale. Compared with Pusher below.
Later

SES, S3 + CloudFront

Invite emails and public hosting come in the last step. Until then, the invite link appears in the app to copy, and the frontend runs locally against the deployed API.

SES costs $0.10 per 1,000 emails.

Data model

One DynamoDB table: PK + SK

Every screen reads with one query. A list page is Query PK = LIST#id, which returns the metadata, items, members and pending invites in one round trip. No secondary index is needed yet.

PKSKAttributesUsed for
USER#{sub}LIST#{listId}role, joinedAt"My lists": query by user, then BatchGet each list's META
LIST#{listId}METAname, ownerId, createdAt, updatedAtList name and owner
LIST#{listId}ITEM#{itemId}text, qty, done, position, updatedBy, updatedAtItems. The ID is a ULID, so items sort by creation time.
LIST#{listId}MEMBER#{sub}email, role (owner | editor)Access check on every request
LIST#{listId}INVITE#{email}token, invitedBy, expiresAt (TTL)"Pending" rows in the share sheet
INVITE#{token}METAlistId, email, invitedBy, expiresAt (TTL)Looking up the invite from the email link
LIST#{listId}CONN#{connectionId}sub, expiresAt (TTL)Who to push a change to
CONN#{connectionId}METAsub, listId, expiresAt (TTL)Cleanup on disconnect

The list name lives only in META, so renaming a list is one write. Deleting a list queries PK = LIST#id, deletes those rows in batches, and also deletes each member's USER#…/LIST#id row.

API Gateway

Two APIs: HTTP for requests, WebSocket for live updates

Both are defined in the CDK ApiStack. We use the HTTP API type, not the older REST API type. It costs about $1 per million calls instead of $3.50, and it checks Cognito tokens with no extra code. We don't need anything that only the REST API type offers, such as API keys, usage plans or response caching.

Cheaper alternative we decided against: Lambda Function URLs have no per-request charge. But bad tokens would then reach Lambda, and we would have to write the token check, routing and throttling ourselves. At this scale it saves about $0.03 a month.

Decision

Live updates: WebSocket API or Pusher?

Both cost $0 or close to it for a project this size. I recommend the AWS WebSocket API. It needs no third-party account and no extra keys, it uses the same Cognito identity, and it has no hard cap on connections.

Recommended

API Gateway WebSocket

  • About $1 per million messages and $0.25 per million connection-minutes
  • Example: 10 people for 2 hours a day is about 36k connection-minutes a month, roughly $0.01
  • Auth on $connect with the same access token. Cognito GetUser verifies it, so we don't need a JWT library.
  • Everything is in one CDK app and one bill
Alternative

Pusher Channels (free Sandbox)

  • $0, capped at 100 concurrent connections and 200k messages a day
  • Private channels still need an auth endpoint, so we'd write a Lambda route anyway
  • Requires a separate account, with app keys stored in Secrets or SSM
  • Going past the cap means a paid plan (from about $49 a month)
Socket messageDirectionShape

API Gateway closes idle sockets after 10 minutes and all sockets after 2 hours. The app pings every 5 minutes, reconnects when the socket closes, and reloads the list after reconnecting, so changes made while it was disconnected are not lost.

Build plan

Five steps, each one deployable

I write the code and the CDK for a step. You run cdk deploy and test it on AWS, and we move on only when the "done when" check passes.

  1. Sign up and log in

    • CDK app skeleton with a dev stage and an AuthStack: user pool, email sign-in, self sign-up, and an app client with no secret using USER_PASSWORD_AUTH
    • Frontend: log in, sign up, confirm code, forgot password, and an empty "My lists" page
    Done when: you sign up with a real email, receive the code, log in, refresh the page and are still logged in.

  2. Lists and items

    • DataStack: the table with TTL enabled. ApiStack: HTTP API, JWT authorizer, and the api Lambda with list and item routes
    • Frontend: My lists, list page, add/edit/check/delete items
    Done when: you create, rename and delete lists and items, and everything is still there after a reload. A request without a token gets a 401.

  3. Live updates

    • WebSocket API and the ws Lambda (connect, disconnect, subscribe). The api Lambda pushes after each write.
    • Frontend: socket client with reconnect, highlight on remote changes, and the "who's here" pill
    Done when: you open the same list in two browsers, and a change in one appears in the other within about a second.

  4. Sharing

    • Routes for invites, accept, cancel, remove member and leave list. Accept checks that the logged-in email matches the invite email.
    • Frontend: share sheet, invite page, and the sign-up path that returns to the invite. The invite link is shown with a copy button.
    Done when: a second account opens the link, signs up, sees the list and gets live updates. Once removed, that account gets a 403.

  5. Email and hosting (last)

    • SES identity, a request for production access, and the invite email template
    • S3 + CloudFront for the frontend. Optional: Google sign-in and CI.
    Done when: an invite reaches someone's inbox, and the app works from its public URL.
